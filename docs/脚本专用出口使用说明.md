# 脚本专用出口 + 脚本控制 API 使用说明

适用版本：Clash Party 2.0.0（本次自建构建，产物见 `dist4\win-unpacked\Clash Party.exe`）

这份文档面向「用 puppeteer / playwright / curl 跑自动化任务，希望每个任务走固定代理出口，并能在失败时换节点重试」的场景。

---

## 1. 这两个功能分别解决什么问题

| 功能             | 作用                                                                                                                         | 你要改的地方               |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------- | -------------------------- |
| **脚本专用出口** | 在本机开一个**独立的代理端口**，这个端口固定走你指定的节点或策略组。脚本用 `--proxy-server=http://127.0.0.1:7900` 指过去即可 | 脚本启动参数（一次性写死） |
| **脚本控制 API** | 开一个受限的本机 HTTP 接口，让脚本在**运行时主动切换**策略组当前节点，用于「任务失败 → 换节点 → 重试」                       | 脚本代码里加几行 fetch     |

两者可以单独用，但组合起来才是完整方案：

```
脚本 --proxy-server=127.0.0.1:7900   →  出口 listener(7900)  →  策略组 SCRIPT-POOL  →  某个节点
                                                                        ↑
脚本 PUT 127.0.0.1:17890/groups/SCRIPT-POOL  ────────────────────────────┘  运行时换节点
```

关键点：**脚本的启动参数永远不用改**，换节点是改「策略组当前选中项」，出口端口不动。

---

## 2. 前置准备：建一个脚本专用策略组

强烈建议**不要**让脚本去切你日常上网用的分组（比如「节点选择」），否则脚本换节点时你的浏览器也会跟着换。

> **已经在用聚合订阅覆写脚本的话，这一节可以跳过。** 覆写脚本已经自动生成了 50 个脚本专用的隐藏 `select` 组 `出口能用01 ~ 出口能用50`（成员 = 「自动选择」+ 全部节点，不在「节点选择」里），直接拿它们当脚本组就行，详见第 2.5 节。

在订阅的「覆写」或本地配置里加一个 `select` 类型的组：

```yaml
proxy-groups:
  - name: SCRIPT-POOL
    type: select
    proxies:
      - cn台湾高速01|BGP|流媒体
      - cn台湾专线01|BGP|流媒体
      - gb英国伦敦|CTCU|0.1x
```

> **必须是 `type: select`。** > `url-test` / `fallback` 组被 API 切换时是「固定（fix）」语义而不是「选择」，语义混乱，且需要额外调 DELETE 才能解除固定。

多个脚本并发跑时建议建多个组，互不干扰：

| 组名                  | 用途                             | 建议节点       |
| --------------------- | -------------------------------- | -------------- |
| `SCRIPT-POOL-AIMZ`    | `mzlone.top`（有 Cloudflare 盾） | 过盾 / 住宅 IP |
| `SCRIPT-POOL-SHEAPI`  | `sheapi.top`（有 Cloudflare 盾） | 过盾 / 住宅 IP |
| `SCRIPT-POOL-XIAOBAI` | `token.dialoguedui.com`（无盾）  | 普通稳定节点   |

## 2.5 脚本专用出口组 `出口能用01~50`（配合批量出口用）

批量出口需要「一个出口对一个组」才能让 N 条出口各自独立选节点。若 N 条出口共用同一个组，
切组会互相踩踏 —— 脚本 A 切走的节点会直接影响正在跑的脚本 B。

**这件事聚合订阅覆写脚本已经替你做好了，不需要再贴任何额外的覆写脚本。**

覆写脚本（`aggregate-groups.js`）在生成 `[能用]` 之后，会紧接着克隆出 50 个成员完全一致的
独立 `select` 组：

| 项               | 值                                            |
| ---------------- | --------------------------------------------- |
| 组名             | `出口能用01` ~ `出口能用50`（不带方括号）     |
| 类型             | `select`                                      |
| 成员             | 与 `[能用]` 逐项一致（`自动选择` + 全部节点） |
| `hidden`         | `true`（全部隐藏）                            |
| 在「节点选择」里 | ❌ 没有                                       |

对应脚本里的三个可调参数（要改数量就改 `OUTLET_COUNT`）：

```javascript
const OUTLET_PREFIX = '出口能用'
const OUTLET_COUNT = 50
const OUTLET_PAD = 2 // 序号补零位数：2 -> 01、3 -> 001
```

### 几个要点

| 要点                        | 说明                                                                                                                        |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `hidden: true`              | mihomo 原生字段。代理页面、托盘菜单、脚本 API 的 `GET /groups`（列表）都不会显示它们，但仍可被出口正常引用                  |
| 出口页面**照样能选到**      | 「脚本专用出口」配置页是唯一会带 `includeHidden` 读取策略组的地方，所以隐藏组在这里可见，可以正常搜索、全选                 |
| 单组接口**不受影响**        | `GET /groups/{组名}` 和 `PUT /groups/{组名}` 走的是另一条不过滤 hidden 的路径，所以脚本照常能查、能切 `出口能用01`          |
| 组名不含方括号              | 叫 `出口能用01`，不是 `[出口能用01]`。在出口目标选择器里搜「出口能用」即可一次筛出 50 个                                    |
| 已删掉旧的裸组 `[出口能用]` | 原来那个单组已从脚本里移除。**如果你还有旧脚本写着 `GROUP = '[出口能用]'`，要改成 `出口能用01` 之类的具体组名**，否则会 404 |
| 不进「稳定」等日常组        | 这 50 个组被刻意排除在 `节点选择` / `稳定` 的可引用目标之外 —— 它们是脚本专属，不该掺进日常上网链路                         |
| 改订阅不会丢                | 覆写是每次生成配置时重新执行的，订阅更新后依然生效                                                                          |

> **不要在覆写脚本里写 `dns` / `tun` / `sniffer` / 端口 / `mode`** —— 这些会被受控配置覆盖，属于无效写法。

配好之后回到「脚本专用出口」页面，用批量新增建 50 条出口，在目标选择器里搜「出口能用」，
一键全选，即可让 `test01~test50` 按顺序 1:1 对应 `出口能用01~出口能用50`。

## 3. 配置脚本专用出口

侧边栏进入「**脚本专用出口**」页面（若侧栏没有，去「设置 → 侧边栏」把它打开）。

点右上角「**新增出口**」，逐项填写：

| 字段                        | 说明                                                                                                        |
| --------------------------- | ----------------------------------------------------------------------------------------------------------- |
| **备注**                    | 随便写，只是给你自己看的，例如 `AIMZ-签到`                                                                  |
| **监听端口**                | 本机端口，例如 `7900`。不能和 mihomo 的混合端口/SOCKS 端口/控制端口重复，也不能和其它出口重复（重复会标红） |
| **入站类型**                | `HTTP + SOCKS5`（默认，推荐）/ 仅 HTTP / 仅 SOCKS5                                                          |
| **出口模式**                | 见下表                                                                                                      |
| **出口目标**                | direct 模式下选一个已有的策略组或节点                                                                       |
| **备选节点**                | fallback 模式下多选节点                                                                                     |
| **健康检查地址 / 检查间隔** | fallback 模式专用                                                                                           |
| **允许 UDP**                | 默认开                                                                                                      |

> **探测工位的端口不用你操心，也不用给它留区间。** `mode:"ip"` 需要 100 个本机端口做探测工位（见 7.9），由程序在生成配置时自动挑：从 `18100` 起往后找**第一段连续 100 个空闲端口**，你已经配好的出口端口它会整段绕开。实际用了哪一段看启动日志的 `Probe stations injected: 100 [18100-18199]`。
>
> 所以你在任意区间加出口都不会把工位挤掉。唯一的例外是本机 `18100 ~ 49151` 之间**再也找不到连续 100 个空端口**，那时日志会有 `no free window of 100 consecutive ports`，`mode:"ip"` 不可用（`mode:"delay"` 不受影响，它走内核测速、不用工位）。

### 两种出口模式怎么选

| 模式                              | 内部行为                                                                         | 什么时候用                                                  |
| --------------------------------- | -------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| **直连指定节点/策略组**（direct） | listener 直接把流量交给你选的那个组或节点，不额外生成任何组                      | **配合脚本控制 API 时必须用这个**，出口目标选 `SCRIPT-POOL` |
| **故障转移组**（fallback）        | 自动生成一个隐藏的 `PARTY-OUTLET-<端口>` fallback 组，做健康检查、节点挂了自动换 | 你不想在脚本里写切换逻辑，让内核自动容错时用                |

> ⚠ fallback 模式生成的 `PARTY-OUTLET-*` 组是**内核托管**的，脚本控制 API 会拒绝切换它（返回 403）。想让脚本自己控节点，就用 direct + 你自己建的 `select` 组。

填完点右上角「**应用并重启内核**」。**不点这个按钮配置不会生效**——出口是写进内核配置文件的，必须重启 mihomo。

出口条目上有个复制图标，点一下会把 `--proxy-server=http://127.0.0.1:7900` 复制到剪贴板。

### 安全说明

出口 listener 的监听地址**固定为 `127.0.0.1`**，不可配置，因此不会在局域网里暴露一个无鉴权代理。

## 3.5 批量新增出口（一张卡片管一批）

如果你要一次开十几个出口（比如十个账号各走一个固定节点），一个个「新增出口」太累。点右上角「**批量新增出口**」，用一张卡片就能管理一整批：

- **备注前缀**：只填一个前缀，比如 `test`，会自动生成 `test01`、`test02`……（个数超过 99 时自动补三位 `test001`）。
- **出口个数**：比如填 `10`，就展开成 10 个出口。上限 200。
- **起始监听端口**：只填一个起始端口，比如 `7900`，端口自动升序占用 `7900 ~ 7909`。整段区间里只要有一个端口和别的出口/内核端口冲突，整张卡片会标红。
- **入站类型 / 出口模式 / 允许 UDP**：整批**共享**，选一次对所有出口生效。
- **出口目标**：见下面两种模式。

> **一张卡片 = 一条配置。** 批量出口在配置文件里只存一条记录（前缀 + 个数 + 起始端口 + 有序目标列表），**只有在「应用并重启内核」注入内核时才展开**成 N 个 listener。以后要改还是在这张卡片上改，不会散成一堆卡片。

### 批量出口的两种模式

| 模式                              | 目标怎么对应                                                                                          | 说明                                                       |
| --------------------------------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| **直连指定节点/策略组**（direct） | 多选目标，按**选中顺序**和端口 1:1 对应：第 1 个目标 → `test01`（7900），第 2 个 → `test02`（7901）…… | 每个出口走各自固定的一个节点/组                            |
| **故障转移组**（fallback）        | 所有出口**共用同一份**备选节点列表                                                                    | 每个端口各生成一个成员相同的 fallback 组，各自独立健康检查 |

### 用目标选择器按顺序挑目标（direct 模式）

direct 模式下点「**选择目标**」打开选择器，这里就是实现「搜出一批、一键全选、按顺序对应」的地方：

1. 左栏输入关键字筛选，比如搜 `出口能用`，就筛出 `出口能用01 ~ 出口能用10`。
2. 点「**全选筛选结果**」，这一批会**按筛选列表的顺序**追加到右栏已选列表。
3. 右栏是最终的顺序：第 1 项对应 `test01`，第 2 项对应 `test02`……可以用上移/下移微调，或单独移除。
4. 已选数量和出口个数不一致时会标黄提示（比如选了 8 个但有 10 个出口）。**目标不够的出口在应用时会被跳过**（预览区里那一行标黄）。

> 举例：备注前缀 `test`、个数 `10`、起始端口 `7900`，direct 模式搜 `出口能用` 一键全选 `出口能用01~10`，就得到 `test01(7900)→出口能用01`、`test02(7901)→出口能用02`…… `test10(7909)→出口能用10`。

### 展开预览

批量卡片底部有「**展开预览**」，逐行列出应用后实际会生成的每个出口（备注 / `127.0.0.1:端口` / → / 目标），所见即所得，和内核里实际注入的 listener 完全一致。卡片顶部的复制图标会把整批的 `--proxy-server=...` 参数一次性复制（每行一个）。

> **注意**：脚本控制 API 的 `GET /outlets` 对批量出口返回的是**展开后**的逐端口列表，条目数等于实际 listener 数，而不是配置里的卡片数。

## 4. 在脚本里使用出口

puppeteer 示例（这是**唯一**需要改的启动参数）：

```javascript
const browser = await puppeteer.launch({
  executablePath: CHROME_PATH,
  userDataDir: profileDir,
  headless: false,
  args: [
    '--proxy-server=http://127.0.0.1:7900',
    // 可选：避免本地地址也走代理
    '--proxy-bypass-list=<local>'
  ]
})
```

验证是否真的走了代理：

```powershell
curl.exe -x http://127.0.0.1:7900 https://api.ipify.org
```

返回的 IP 应该是你选的节点的 IP，而不是你的家宽 IP。

## 5. 配置脚本控制 API

同一个「脚本专用出口」页面，下方有「**脚本控制 API**」卡片。

1. 点「**生成随机令牌**」——会生成一个 48 位十六进制令牌并自动应用。
2. 确认「**监听端口**」，默认 `17890`（不能和出口端口冲突，冲突会标红）。
3. 「**切换后断开旧连接**」建议保持开启：切节点后旧的 TCP 连接仍在复用老节点，断开才能让新节点立刻生效。
4. 打开「**启用脚本控制 API**」开关。
5. 左边的状态标签变成绿色的 `127.0.0.1:17890` 表示已在运行；点复制图标可以复制接口地址和令牌。

> **令牌不能为空。** 留空时服务端会直接拒绝启动并在日志里打 `Script API is enabled but token is empty, refusing to start`。原因很直白：本机无鉴权 HTTP 接口任何本地程序（包括你随便打开的网页）都能调，等于把代理控制权交给全机器。

这个 API 和 mihomo 自带的 `external-controller` 是**两回事**——它只暴露下面 7 个端点，不暴露 `/configs`、`/connections`、`/providers` 等敏感接口。

## 6. API 接口清单

基址：`http://127.0.0.1:17890`
所有请求都必须带请求头：`Authorization: Bearer <你的令牌>`

| 方法    | 路径                 | 说明                                                                                                                                                                           |
| ------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| GET     | `/ping`              | 存活检查，返回 `{ "ok": true, "service": "clash-party-script-api" }`                                                                                                           |
| GET     | `/groups`            | 列出所有策略组：`name` / `type` / `now`（当前节点）/ `fixed` / `proxies`（成员列表）                                                                                           |
| GET     | `/groups/{组名}`     | 查询单个组当前选中的节点                                                                                                                                                       |
| **PUT** | **`/groups/{组名}`** | **切换该组当前节点**，请求体 `{"name": "节点名"}`；`?close=0` 可抑制本次的全局断连（见下）                                                                                     |
| DELETE  | `/groups/{组名}`     | 解除 url-test / fallback 组的固定选择，恢复自动测速                                                                                                                            |
| POST    | `/probe`             | 探测。请求体带 `proxies` 数组 = 只查这批节点（`mode:"delay"` 查延迟见 7.8，`mode:"ip"` 实拨拿真实出口 IP 见 7.9）；不带 `proxies` = 跑一轮全量基线（600 多个节点实测约 18 秒） |
| POST    | `/reload`            | 重新生成配置并热重载内核。**改策略组成员名单**唯一的生效途径（见 6.1）                                                                                                         |
| GET     | `/outlets`           | 列出已配置的脚本出口（端口 / 开关 / 模式 / 目标），用于脚本自检                                                                                                                |

> 两个 GET `/groups` 接口支持 `maxDelay` 等延迟过滤参数，用来只拿「能用」的节点，见第 7 节。不带这些参数时行为和以前完全一样。

### 6.1 `PUT ?close=0` 与 `POST /reload`

这两个都是给「批量探测 + 自动更新名单」这类脚本准备的，日常轮换用不到。

**`PUT /groups/{组名}?close=0`**

设置里的 `autoCloseConnection` 打开时，每次切换都会断开内核**全部**连接 —— 目的是让正在复用旧节点的连接立刻改走新节点。但批量探测一轮要切几百次，每次都清场会把你正在跑的浏览器、下载反复掐断。

带上 `?close=0` 就跳过这一次的断连。探测走的是独立出口端口，新建连接自然用新节点，本来就不需要清场。不带这个参数时行为和以前完全一样。

**`POST /reload`**

先分清两件不同的事：

| 你要做的事                 | 用什么                          | 要不要 reload |
| -------------------------- | ------------------------------- | ------------- |
| 换某个组**当前选中**的节点 | `PUT /groups/{组名}`            | 不要          |
| 换某个组的**成员名单**     | 改覆写脚本，然后 `POST /reload` | **要**        |

成员名单属于配置文件内容，mihomo 的 `PATCH /configs` 只吃 mode / log-level / 端口 / tun / sniffer 这类运行时开关，**不接受 `proxy-groups`**。所以改名单只能重写 work config 再让内核整图重载，这正是 `/reload` 做的事（内部含 `generateProfile()`，会重新执行覆写脚本；内核没在跑时自动退化成重启内核）。

另外，`override/*.js` 没有文件监听。脚本改完覆写文件若不调 `/reload`，改动会一直等到你下次在界面里动配置才生效。

⚠ 副作用：整图重建会**中断进行中的连接**（一次）。别放在循环里调，建议安排在夜间。

各 select 组的当前选中项**不保证**保留。2026-08-29 同一天两次实测，一次 `过盾` 组的 `now` 保持不变，另一次回落成了组的第一个成员（`过盾-自动`）—— 两次原选中节点都仍在新名单里，没能定位差异原因。所以要固定某个节点的话，reload 之后自己再 `PUT` 一次，别指望内核帮你记住。

### 错误码对照

| 状态码 | 消息                                                           | 原因                                                      |
| ------ | -------------------------------------------------------------- | --------------------------------------------------------- |
| 401    | `invalid or missing token`                                     | 没带或带错 `Authorization`                                |
| 403    | `only loopback requests are allowed`                           | 非本机请求                                                |
| 403    | `group ... is managed by script outlet and cannot be switched` | 试图切 `PARTY-OUTLET-*` 或探测工位 `PARTY-PROBE-*` 隐藏组 |
| 400    | `body.name is required`                                        | PUT 没传节点名                                            |
| 400    | `proxy ... is not a member of group ...`                       | 目标节点不在该组成员列表里                                |
| 400    | `unknown mode: xxx (expected "delay" or "ip")`                 | `POST /probe` 的 `mode` 只认这两个值                      |
| 404    | `group not found: ...`                                         | 组名不存在（注意大小写和特殊字符）                        |
| 404    | `unknown endpoint`                                             | 路径写错                                                  |

> 组名含 `|`、空格、中文时，URL 里必须 `encodeURIComponent`。

## 7. 只拿「能用」的节点（延迟过滤）

### 7.1 为什么需要这一节

`GET /groups` 默认返回组里的**全部**成员。成员里必然混着已经挂掉的、慢到没法用的节点 —— 拉到名单直接用第一个，很可能一上手就是死节点。

给请求加一个 `maxDelay` 参数，就只返回延迟达标的节点：

```
GET /groups/%E5%87%BA%E5%8F%A3%E8%83%BD%E7%94%A801?maxDelay=1000
```

（组名 `出口能用01` 过一遍 `encodeURIComponent` 就是上面那串。）

> **脚本请用 `出口能用01~50`，不要用 `[能用]`。** 它们都是覆写脚本自动生成的 `select` 组，成员逐项一致，区别只在分工：
>
> | 组名              | 用途               | 在「节点选择」里 | 代理页面                    |
> | ----------------- | ------------------ | ---------------- | --------------------------- |
> | `[能用]`          | 你自己在 UI 上手切 | ✅ 有            | ✅ 显示                     |
> | `出口能用01`~`50` | 脚本专用           | ❌ 没有          | ❌ 不显示（`hidden: true`） |
>
> 切组是全局操作。拆开之后，脚本每轮 `PUT` 换节点只动自己那一个 `出口能用NN`，既不会动你浏览器正在用的出口，也不会和别的脚本互相抢选中项。脚本专用出口（第 3 节）的「出口目标」也应该选 `出口能用NN`。
>
> **一条出口对应一个组**：出口 `test01` 配 `出口能用01`、`test02` 配 `出口能用02`，以此类推。

### 7.2 ⚠ 最重要的一件事：这个接口不会替你现测

**`GET /groups` 返回的延迟数字全部来自程序自己维护的「探测结果表」，不是请求时现场测的。**

表由两个地方写入：

| 写入方                        | 时机                                                                                                  | 测什么           | 职责                                       |
| ----------------------------- | ----------------------------------------------------------------------------------------------------- | ---------------- | ------------------------------------------ |
| 全量基线                      | 启动 20 秒后 + 之后每 **3 小时**一轮（默认值，可在出口页面改，`0` = 关掉周期轮）+ 订阅更新 / 切配置时 | 全部节点         | **保覆盖**：让每个节点都至少有一条记录     |
| `POST /probe`（带 `proxies`） | 你调的时候                                                                                            | 只测你点名的那批 | **保新鲜**：热点节点的数据由脚本自己按需刷 |

所以：

- **`GET /groups?maxDelay=...` 默认立刻返回**，不会挂着等探测。旧版本「数据过期就顺手测一轮」的行为已经删掉了 —— 那条路会让一个只想读名单的请求突然等十几秒。
- 想强制刷新，两种办法：
  1. 带 `wait=1`：同步跑一轮**全量基线**再返回（600 多个节点实测约 18 秒，超时要给足）。
  2. 用 `POST /probe` 带 `proxies`：只测你关心的那几十个，快得多。**推荐这个。**
- 响应里的 `filter.dataAgeMs` / `filter.stale` 告诉你这批数据有多旧，`filter.storeSize` 告诉你表里一共有多少条记录 —— **表为空（`storeSize=0`）说明启动基线还没跑完**，此时名单一定是空的。

> `wait=1` 刻意**不受 `maxAge` 刹车**：你明确要求现测就一定会测。并发的 `wait=1` 会 join 同一轮，不会叠加压力。

### 7.2.1 基线周期为什么默认 3 小时（以及怎么改）

因为流量。实测单次测速的真实流量是 **8.01 KB**（TLS 握手占 65%），642 个节点算下来：

| 基线周期         | 月流量     |
| ---------------- | ---------- |
| 3 小时（默认值） | 约 0.12 GB |
| 30 分钟（旧值）  | 7.06 GB    |
| 5 分钟           | 42.4 GB    |

机场按流量计费，把基线压到 5 分钟去「保新鲜」是拿 42 GB 换一件本来该由 `POST /probe` 按需做的事 —— 而且绝大多数被测的节点脚本根本不会用到。所以切法是：**基线低频保覆盖，`POST /probe` 按需保新鲜。**

**这个周期现在可以自己改**：设置页 → 「出口脚本」→ **全量测速间隔（分钟）**。几条取值规则：

| 你填的值            | 实际行为                                       |
| ------------------- | ---------------------------------------------- |
| `180`（默认）       | 每 180 分钟一轮                                |
| `0`                 | **关掉周期轮**（首轮与事件触发仍然会跑，见下） |
| `1` / `3`（小于 5） | 夹到下限 **5 分钟**                            |
| 留空 / 非法值       | 回落默认 180                                   |

下限定在 5 分钟也是流量账算出来的：566 个节点一轮约 4.5 MB，5 分钟一轮 = 288 轮/天 ≈ 1.3 GB/天 ≈ 40 GB/月。再往下就不是「高频」而是烧钱了。

> ⚠ `0` 的语义是「不要每隔一段时间自动测」，**不是「永远不测」**。启动后 20 秒的首轮打底、以及订阅更新 / 切配置 / 热重载的触发照跑。否则接下来这一条自锁会让你的脚本永远拿到空名单。

反过来，基线也不能取消：脚本问「这个组里哪些能用」时，表里没记录的节点一律判不可用 → 不出现在名单 → 脚本永远不会拿它的名字去 `POST /probe` → 永远不进表。这个自锁不会自愈，只有全组覆盖的基线能打破它。

### 7.3 查询参数

| 参数       | 默认                           | 说明                                                                                                                                                                                    |
| ---------- | ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `maxDelay` | 不带则**完全不过滤**（老行为） | 延迟上限（毫秒），只保留 `0 < 延迟 ≤ maxDelay` 的节点。写成 `maxDelay=auto` 或留空值时，取设置页「内核设置 → 「能用」延迟阈值」的数值（默认 1000）                                      |
| `maxAge`   | `300`（5 分钟）                | **只影响响应里 `filter.stale` 这个提示位**，单位秒，下限 30 秒。⚠ 它**不再触发探测** —— 数据旧了也照样立刻返回，`stale=true` 只是告诉你「这批数据超过你要求的年龄了，自己决定要不要刷」 |
| `wait`     | `0`                            | `1` = 先同步跑一轮**全量基线**再返回（约 18 秒）；`0` = 立刻返回表里现有的数据。⚠ **默认值从 `1` 改成了 `0`**：读名单是高频操作，不该顺带触发全量探测                                   |

> 想刷新少量节点请用 `POST /probe` + `proxies`，不要用 `wait=1` —— 后者是整份订阅全测一遍。

### 7.4 过滤口径（记住这几条就不会被坑）

| 情况                                                            | 结果    |
| --------------------------------------------------------------- | ------- |
| 延迟在 `(0, maxDelay]`                                          | ✅ 返回 |
| 延迟 = 0（连不上）                                              | ❌ 剔除 |
| 延迟 > `maxDelay`（太慢）                                       | ❌ 剔除 |
| **从来没测过**（探测结果表里没有它的记录）                      | ❌ 剔除 |
| 成员本身是**策略组**（比如 `出口能用01` 里的第一项 `自动选择`） | ❌ 剔除 |

后两条容易踩：

- **「没测过就不给」是故意的。** 脚本要的是「保证能用」，没有数据就不能算能用。代价是**刚开机头 20 秒名单可能是空的**（第一轮全量还没跑），脚本要能容忍 —— 建议名单为空时先 `POST /probe` 再重试一次。
- **策略组被剔除**，因为组的延迟归属不清（测组等于测它当前选中的那个节点）。但你仍然可以用 `PUT` 显式切到组，比如切到 `自动选择` 让内核自己挑 —— `PUT` 不做延迟校验，你点名谁就切谁。

带 `maxDelay` 时，`GET /groups/{组名}` 的响应会多出这些：

  "type": "Selector",
  "now": "[SecOne] 🇯🇵 日本 [ANYTLS] 03",

| 字段                     | 用途                                                                                                          |
| ------------------------ | ------------------------------------------------------------------------------------------------------------- |
| `proxies`                | 已按延迟**升序**排好，直接取 `proxies[0]` 就是当前最快的                                                      |
| `details`                | 每个节点的延迟、测量时间和数据年龄 `ageMs`，想自己排序或打日志时用                                            |
| `total` / `usable`       | 全部成员数 / 达标数                                                                                           |
| `filter.probed`          | 本次请求是否等了一轮全量基线（即你有没有带 `wait=1`）                                                         |
| `filter.dataAgeMs`       | 表里最新一条记录是多少毫秒前写的，`null` 表示表是空的（从未探测过）                                           |
| `filter.stale`           | `dataAgeMs > maxAge`。**只是提示**，不代表本次返回的数据无效                                                  |
| `filter.storeSize`       | 探测结果表里一共有多少条记录。`0` = 启动基线还没跑完，此时 `usable` 必然是 0                                  |
| `filter.storeAlive`      | 表里有多少条是「测得通」的。配合 `storeSize` 判因：`storeSize>0` 而 `storeAlive=0` → 确实全都不通，不是没数据 |
| `filter.lastProbedCount` | 最近一轮**基线**覆盖了多少个节点（不含 `POST /probe` 的局部探测）                                             |

`GET /groups`（列全部组）带 `maxDelay` 时，每个组也会有 `proxies` / `total` / `usable`，但**没有 `details`、也不排序**。要排好序的名单就查单个组。

### 7.6 名单再新鲜也不保证一定通

节点能回 `generate_204` 不等于它能连上你脚本真正要访问的那个站（可能被目标站封了 IP、可能有盾）。所以**名单只负责把明显不可用的先筛掉，重试逻辑不能省**：拿名单 → 试第一个 → 失败换下一个。有了重试，名单是 1 分钟前还是 20 分钟前测的就都不太要紧了。

### 7.7 推荐用法

```javascript
const GROUP = '出口能用01' // 脚本专用组，别写成 [能用]（那个是你自己手切用的）
// 多个脚本并发跑时，每个脚本各用一个：出口能用01 / 出口能用02 / ……

/** 拿一批当前可用的节点，已按延迟从快到慢排好 */
async function fetchUsableNodes(maxDelay = 1000) {
  const path = `/groups/${encodeURIComponent(GROUP)}?maxDelay=${maxDelay}`
  // 这个请求不会现测，正常情况下毫秒级返回
  let info = await ctrl(path)

  if (info.proxies.length === 0 && info.filter.storeSize === 0) {
    // 表是空的 —— 刚开机、启动基线还没跑完。催一轮全量（约 18 秒），超时要给足
    await ctrl('/probe', { method: 'POST' })
    info = await ctrl(path)
  }

  console.log(
    `[代理] 可用 ${info.usable}/${info.total}，数据 ${info.filter.dataAgeMs}ms 前测的` +
      `（表 ${info.filter.storeAlive}/${info.filter.storeSize}）`
  )
  return info.proxies
}

/** 用完名单后，对真正要用的那几个刷一次新鲜延迟 */
async function refreshDelays(names, maxDelay = 1000) {
  const res = await ctrl('/probe', {
    method: 'POST',
    body: JSON.stringify({ mode: 'delay', proxies: names, maxDelay })
  })
  // 只要 usable 的，已经按你给的 maxDelay 过滤过
  return res.results.filter((r) => r.usable).map((r) => r.name)
}
```

然后把下一节里写死的 `NODES` 常量换成 `await fetchUsableNodes()` 的返回值即可 —— 轮换逻辑一行都不用改。

#### 参数

| 字段          | 默认      | 说明                                                                                                                                                                                             |
| ------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `proxies`     | 必填      | 节点名数组。**最多 400 个**，超出的部分静默截断（不报错），截掉多少看 `limits.truncated`                                                                                                         |
| `mode`        | `"delay"` | `"delay"` 查延迟；`"ip"` 实拨查真实出口 IP（见 7.9）。其它值返回 400                                                                                                                             |
| `maxDelay`    | 不过滤    | **只用于给结果打 `usable` 标记**，不影响怎么测。传 0 或不传 = 不过滤（`usable` 等价于 `delay > 0`）                                                                                              |
| `maxAge`      | `300`     | 秒。表里的记录只要不老于这个值就直接返回，否则**现测一次**。`0` = 强制现测                                                                                                                       |
| `probeUrl`    | 见下      | 覆盖本次的测速地址，必须是 http/https，解析不出来就当没传。默认取「设置 → 内核设置 → **脚本探测测速 URL**」，再退到同一页的「延迟测试 URL」，最后是内置的 `https://www.gstatic.com/generate_204` |
| ~~`timeout`~~ | —         | **已废弃并被忽略。** 传了会在响应里回一个 `timeoutIgnored: true` 提醒你。原因见下面「为什么不让你传 timeout」                                                                                    |

#### ⚠ 为什么不让你传 timeout（这是本项目修过的最严重的一个 bug）

测速 timeout 现在**固定 6000ms**，脚本无法修改，`maxDelay` 也**绝不会**被换算成 timeout。

原因是 mihomo 把两个正交的量混在了一个参数上：它的 `GET /proxies/{name}/delay` 把 `timeout` 当作**整个操作**的 deadline（dial → TLS 握手 → HEAD#1 → HEAD#2），而返回的 `delay` 只是**最后那一个 RTT**（因为本项目模板默认 `unified-delay: true`）。实测「墙钟耗时 / 上报延迟」的比值 p50 = 7.2、p90 = 16.9。

所以旧版本的 `timeout=1200` 真实语义不是「筛掉延迟大于 1200ms 的节点」，而是「筛掉整链耗时大于 1200ms 的节点」≈「RTT 超过 200ms 就出局」—— 一道比名义阈值严好几倍的暗门。分层抽样 97 个节点、以「切组后从本地端口实拨真实 https 站点」为真实判据交叉验证：

| timeout | 召回率 |
| ------- | ------ |
| 1200    | 15.8%  |
| 2500    | 57.9%  |
| 5000    | 89.5%  |

而且 `timeout=1200` 时 97 个失败里 **75 个是 504（被 deadline 截断，节点其实健康）**，只有 16 个是 503（真连不上）。

放宽 timeout **不会**放宽质量标准：上报的延迟数值本身跟 timeout 无关（同一节点 @1200 与 @10000 实测是 320/312、188/176、208/229，差异只是节点抖动），放宽只是让节点有机会拿到数字。所以正确姿势是**测量给足，判定分离**：统一用 6000ms 测，拿到数值后再按你的 `maxDelay` 过滤。

这也是为什么不能改成「由 `maxDelay` 换算 timeout」—— 那只是让同一个 bug 换个形式复活，而且这次是由脚本亲手打开那道暗门。

#### `err` 错误码：`delay=0` 现在能区分原因了

旧版本所有失败都是 `delay=0`，看不出是「超时」还是「节点死了」还是「内核没起来」。现在每条失败都带 `err`：

| `err`          | 含义                                   | 脚本该怎么办                                                |
| -------------- | -------------------------------------- | ----------------------------------------------------------- |
| `timeout`      | 6000ms 内没跑完整链（内核回 504）      | 节点可能只是慢或抖，**值得重试**，不要立刻拉黑              |
| `unreachable`  | 内核连不上落地（回 503）               | 节点大概率真的坏了                                          |
| `tls_failed`   | TLS 握手被拒                           | 落地机或中间链路问题                                        |
| `bad_response` | 连上了但响应不对（劫持 / 门户页）      | 出网被拦，换节点                                            |
| `dial_failed`  | 连**本地**端口都失败                   | 与远端节点无关，是本机工位/内核问题（只出现在 `mode:"ip"`） |
| `kernel_error` | 其它内核侧异常（内核没起来、管道断了） | 与节点质量无关，别记到节点账上                              |

`delay > 0` 时 `err` 恒为 `null`，不会出现「有延迟数字又同时报错」的组合。

#### 名单是怎么被处理的

顺序是**先去重、再校验、最后才截断**，所以重复名、不存在的名、策略组名都不占那 400 个额度：

| 情况                                 | 结果                               |
| ------------------------------------ | ---------------------------------- |
| 重复出现的名字                       | 只保留第一次出现的位置，测一次     |
| 内核里查不到（订阅更新后失效）       | 跳过，列进 `unknown`，请求照常成功 |
| 传的是策略组名                       | 拒测，列进 `rejected`              |
| `DIRECT` / `REJECT` / `PASS-RULE` 等 | 拒测，列进 `rejected`              |
| 去重校验后仍超过 400 个              | 保留**前 400 个**，其余丢弃        |

> ⚠ **数组顺序在这个接口里是有意义的** —— 和其他接口不一样。超过 400 个时保留的是前 400 个，所以**把你最在意的节点放数组前面**。被丢掉的名字不会回给你（你自己 `slice(400)` 就知道是哪些），响应里只回计数。

#### 耗时怎么估（重要：耗时是跳变的，没有中间档）

命中缓存的名字不花时间，只有**需要现测的**那些才花。同时在飞的探测连接数上限是 **150**，timeout 固定 6000ms，所以：

```
最坏耗时 ≈ ceil(未命中数 / 150) × 6000ms
```

实测三个档位（当时上限是 200）：**1 波 6.3 秒 / 2 波 12.6 秒 / 3 波 17.7 秒**。注意这是**离散**的 —— 名单从 150 个变成 151 个，耗时直接从 6 秒跳到 12 秒。想更快只能减少要测的节点数（或提高 `maxAge` 让更多名字命中缓存），**不能靠加并发**。

稳态下大部分名字都命中 300 秒的新鲜期（看响应里的 `counts.fresh`），实际耗时远低于上式。

**这 150 是全局共享的，而且不只属于这个接口。** 它是**所有**探测流量的总闸门，三条路径共用一份额度：

| 谁在用                     | 什么时候                                      |
| -------------------------- | --------------------------------------------- |
| 全量基线                   | 每隔 N 分钟把整份订阅测一遍（见 7.2.1）       |
| `POST /probe` `mode=delay` | 你调的时候                                    |
| `POST /probe` `mode=ip`    | 你调的时候（**一个节点占 3 个名额**，见 7.9） |

所以：两个脚本同时各测 400 个，总并发仍然是 150；如果此时刚好赶上一轮全量基线，大家一起排队，三方互相拖慢。这是刻意设计的：闸门存在的意义是保护内核和机场，不是保证单个请求的速度。**看到并发时变慢不要当成 bug。**

⚠ **本接口不承诺响应时间**，请求超时至少给 20 秒。之所以不做 SLA，是因为唯一能保证「2 秒内返回」的做法是返回旧值或返回「不确定」，而这两条都被明确否掉了 —— 你要的是「这一刻能用」，给你一条 20 分钟前的数据再标个 `ageMs`，等于把判断责任推回给脚本。

#### 为什么上限是 150 而不是更高

ABABA 交替对照实测（全量 642 个 @timeout=6000，交错排列已排除时间趋势）：

| 并发 | 耗时  | 测活数                   |
| ---- | ----- | ------------------------ |
| 200  | 17.7s | 172~206（均值 191.5）    |
| 300  | 12.2s | 146（−15%）              |
| 400  | 12.3s | 156（−9%）               |
| 不限 | 6.4s  | 80~130（均值 103，−40%） |

档内波动（50/29）远小于档间差距（88.5），所以**高并发确实会把健康节点打成 `delay=0`**，质变从 300 开始。

后来又加了一层判据：除了看探测自己准不准，还用**独立哨兵**（mixed-port + TUN 两条通道、固定 100ms 节奏）量你自己上网被影响得多厉害：

| 并发 | 哨兵 p90（代理/TUN） | 哨兵失败率    |
| ---- | -------------------- | ------------- |
| 100  | 1475 / 1730 ms       | **0%**        |
| 200  | 1669 / 1919 ms       | 0.26% / 0.53% |
| 300  | 2438 / **5213** ms   | **1.25%**     |
| 400  | 2090 / 2172 ms       | 1.46%         |

300 是质变点（TUN p90 飙到 5 秒、失败率首破 1%），200 档已经能测到哨兵失败，100 档才回到 idle 噪声。150 是「留一点吞吐」与「别碰质变点」的折中 —— 而且它现在是三方共用的总额，比旧的 200 更保守是必要的。

⚠ 实测到的**最狠场景不是单路高并发，而是两路叠加**：旧版本里全量基线不占名额，它与这个接口的 200 叠到峰值 400 时，哨兵 p50 直接翻倍（547→1137 / 588→1473ms）、失败率 5.7%/6.2% —— 比「一次性把 566 个节点全部并发拨出去」还差。**局部限流推不出全局有界**，这就是现在三条路径必须共用同一个闸门的原因。

（顺带说明：早前那份实测报告里「降到串行也不改善达标率」的观察是对的 —— 因为当时的瓶颈是 timeout=1200 那道暗门，不是并发。并发效应是在 timeout 给足之后才显现出来的另一个独立因素。）

#### 三个要注意的点

- **不要拿它当高频轮询用。** 每次现测都是真实流量（单节点约 8 KB），而且会挤占那 150 个全局名额（连全量基线和 `mode=ip` 一起挤）。它适合的场景是「我手上这批节点，现在到底哪些能用」，不是每秒刷一遍。默认 `maxAge=300` 已经帮你把重复调用收敛成每 5 分钟真测一轮。
- **`err` 要区别对待。** `timeout` 值得重试，`unreachable` 基本可以拉黑，`kernel_error` 跟节点无关。全都当成「节点坏了」会误杀一批健康节点 —— 这正是旧版本的毛病。
- **它不刷新全局数据的新鲜度。** 局部测几个节点不代表整份名单变新了，所以响应里的 `dataAgeMs` 反映的是**最近一轮全量基线**的年龄，不是本次测出来的年龄。这是刻意的：`lastProbeAt` 代表「基线覆盖面的新鲜度」，让局部探测去刷它会让 `GET /groups` 的陈旧提示失真。

#### 它和 `mode:"delay"` 的根本区别

|                | `mode:"delay"`                               | `mode:"ip"`                            |
| -------------- | -------------------------------------------- | -------------------------------------- |
| 谁在测         | 内核自己的测速接口                           | app 占用**探测工位**真实拨号           |
| 资源性质       | **弹性**：十个脚本一起压，结果是各自排队变慢 | **刚性**：工位有限，超了要排队         |
| 单请求上限     | 400 个名字                                   | **50 个**名字                          |
| 缓存           | 有（`maxAge`，默认 300 秒）                  | **无，每次都现测**                     |
| 占多少闸门名额 | 1 个节点 = 1 条连接 = **1 个名额**           | 1 个节点并行拨 3 个目标 = **3 个名额** |
| 会不会互相踩   | 不会                                         | 靠工位隔离；池子被占满时排队           |

之所以只有 ip 模式需要工位：拿真实 IP 必须先 `PUT` 把某个组切到这个节点、再从对应的本地端口出去。而**切组是全局可见的副作用** —— 两个请求争同一个组不是排队问题，是互相踩：A 切到节点 X，B 立刻切到 Y，A 的拨测就从 Y 出网了，结果串味而且无法察觉。所以每个并发单位必须独占一个「组 + 端口」，这就是工位。

#### 工位池与配额

- 池子共 **100 个**工位（隐藏组 `PARTY-PROBE-<端口>` + 同号监听端口，由程序自动注入，你不用配）。
- **工位端口不是固定区间**。程序在生成配置时从 `18100` 起往后找第一段连续 100 个空闲端口，把你已配置的出口端口、内核入站端口、控制端口整段绕开。实际区间看启动日志：`Probe stations injected: 100 [18100-18199]`。组名和 listener 名都由**端口**派生（不是由序号派生），所以窗口整段平移时组名 ↔ 端口的对应关系不会错位。
- **单个请求最多同时占 50 个**，剩下的留给其他脚本。这是刻意的：如果单请求配额等于池大小，一个脚本就能把工位全占死。
- 工位是**逐个**归还的，不是攒到请求结束一起还，所以后来的脚本能在前一个还在跑的时候就拿到工位。
- `stations.granted` 告诉你本次实际拿到了几个 —— 池子紧张时它会小于 50，表现是耗时变长，不是报错。
- 切配置 / 订阅更新后工位池会**整体重置**并重新预检（同一时刻正在跑的 ip 请求可能报 `dial_failed`，重试即可）。
- 拿了工位却没归还的情况由一个 1 秒周期的巡检**强制回收**（超过 6 秒的租约）。工位泄漏是不可恢复的 —— 池子只会单向变小直到全部卡死，所以这道兜底与业务逻辑无关，永远在跑。

> ⚠ **工位不是唯一的阀门：拨测还要过全局探测闸门（150 条连接）。** 一个节点会并行拨三个回显目标，所以它一次占 **3 个名额**（名额按连接数算而不是节点数）。worker 总是**先领闸门名额、再拿工位**：反过来会让租约里包含排队时间，被上面那个 watchdog 当成泄漏强制回收，两个 worker 就会同时切同一个组 —— 正是工位机制要防的串味。实际含义：`mode=ip` 与全量基线、或与其他脚本的 `mode=delay` 同时跑时会变慢，但不会把网络压垮。

> 这些 `PARTY-PROBE-*` 组是保留的，脚本 `PUT` 它们会被 403 挡住（和 `PARTY-OUTLET-*` 一样）。

#### 每条结果的耗时怎么读

`totalMs = queueMs + connectMs + responseMs`：

| 字段         | 含义                                                       |
| ------------ | ---------------------------------------------------------- |
| `queueMs`    | 排队等工位 + `PUT` 切组的耗时（切组实测 p50 只有 14~15ms） |
| `connectMs`  | 从本地工位端口经该节点建连（含 TLS 握手）的耗时            |
| `responseMs` | 目标站点返回内容的耗时                                     |
| `target`     | 最终是哪个目标拿到了结果                                   |
| `loc`        | 地区码，**只有 cf-trace 这个目标会给**，另两个目标只有 IP  |

#### 三个目标并行，第一个成功就掐断其余

三个目标各自的成功率几乎一样（实测 79/77/80 与 86/85/88），但**失败集合不同**：两轮实测里 cf-trace 失败的节点分别有 9 个和 5 个被另外两个目标救回来，并集召回 88/100 与 91/100。被救回的全是 cf 超时，集中在特定机场的 SSR/HTTP 与 VMESS 节点上。

并行而不是串行：三目标串行全打 28.4s（槽位均值 4192ms），并行取最快 10.6s（槽位均值 1595ms）—— 快 2.7 倍，并集召回还略高。

每个目标的超时封顶 **2500ms**，这个值有实测依据，不要往下压：成功项的 `totalMs` 分布是 p50 ≈ 1050、p90 ≈ 1500~1680、max ≈ 2400，压到 1641 以下会砍掉 7~11 个本来能成功的节点。也不要往上放：吞吐瓶颈在失败项，100 个节点 / 17 工位 / timeout=5000 时，20 个失败节点会吃掉总工作量的 52%。

#### ⚠ 两个必须知道的坑

1. **ip 模式失败 ≠ 节点不可用。** 目标站点自身的抖动会造成 5~9% 的假阴性。判可用性请用 `mode:"delay"`，不要照着 ip 模式的失败去拉黑节点。
2. **出口 IP 大量共用。** 实测 91 个可用节点只对应 **70 个唯一出口 IP**，单个 IP 最多被 4 个节点名共用。**把节点数当出口数会高估容量** —— 如果你的业务是「一个账号一个 IP」，必须按 `ip` 去重后再算。

## 8. 脚本侧节点轮换代码

把下面这段放进你的签到脚本，把 `runWithNodeRotation` 包在单个账号的任务外面：

```javascript
// ============ 代理节点轮换（Clash Party 脚本控制 API） ============
const CTRL = 'http://127.0.0.1:17890' // 脚本控制 API 地址
const TOKEN = '在 UI 里生成并复制过来的令牌'
const GROUP = 'SCRIPT-POOL' // 你自建的 select 组；用覆写脚本的话写 '出口能用01'
const NODES = ['cn台湾高速01|BGP|流媒体', 'cn台湾专线01|BGP|流媒体', 'gb英国伦敦|CTCU|0.1x']

async function ctrl(path, options = {}) {
  const res = await fetch(`${CTRL}${path}`, {
    ...options,
    headers: {
      'Content-Type': 'application/json',
      Authorization: `Bearer ${TOKEN}`,
      ...options.headers
    }
  })
  const text = await res.text()
  if (!res.ok) throw new Error(`脚本控制 API ${res.status}: ${text}`)
  return text ? JSON.parse(text) : null
}

/** 启动前自检：API 是否在跑、组和节点是否都存在 */
async function checkProxyEnv() {
  await ctrl('/ping')
  const info = await ctrl(`/groups/${encodeURIComponent(GROUP)}`)
  const missing = NODES.filter((n) => !info.proxies.includes(n))
  if (missing.length) {
    throw new Error(`以下节点不在 ${GROUP} 组里：${missing.join(', ')}`)
  }
  console.log(`[代理] ${GROUP} 当前节点：${info.now}`)
}

async function switchNode(nodeName) {
  await ctrl(`/groups/${encodeURIComponent(GROUP)}`, {
    method: 'PUT',
    body: JSON.stringify({ name: nodeName })
  })
  console.log(`[代理] 已切换到 ${nodeName}`)
}

/** 依次换节点重试，直到 taskFn 成功 */
async function runWithNodeRotation(taskFn, maxAttempts = NODES.length) {
  let lastErr
  for (let i = 0; i < maxAttempts; i++) {
    const node = NODES[i % NODES.length]
    try {
      await switchNode(node)
      // 服务端已自动断开旧连接，这里再等一下让新连接稳定
      await new Promise((r) => setTimeout(r, 1500))
      return await taskFn(node)
    } catch (err) {
      lastErr = err
      console.warn(`[重试] 节点 ${node} 失败：${err.message}`)
    }
  }
  throw new Error(`所有节点均失败，最后错误：${lastErr?.message}`)
}
```

用法（在你现有的账号循环里）：

```javascript
await checkProxyEnv() // 开跑前自检一次

for (const profile of profiles) {
  try {
    await runWithNodeRotation(async (node) => {
      console.log(`[${profile}] 使用节点 ${node} 开始签到`)
      await signIn(profile) // 你原来的签到逻辑
    })
  } catch (e) {
    console.error(`[${profile}] 全部节点都失败：${e.message}`)
  }
  await sleep(5000 + Math.random() * 7000)
}
```

### ⚠ 多脚本并发时的陷阱

切换策略组是**全局操作**。如果三个 PM2 任务同时在跑，A 脚本切了 `SCRIPT-POOL`，B 脚本正在用同一个组的浏览器会被一起换掉。

两种解法，任选：

1. **一脚本一组一端口**（推荐）：
   | 脚本 | 策略组 | 出口端口 |
   |---|---|---|
   | `aimz_auto_signin.js` | `SCRIPT-POOL-AIMZ` | 7900 |
   | `xiaobai_auto_signin.js` | `SCRIPT-POOL-XIAOBAI` | 7901 |
   | `sheapi_auto_signin.js` | `SCRIPT-POOL-SHEAPI` | 7902 |

2. 在 `ecosystem.config.js` 里用 `cron_restart` 错开时间，让三个脚本不同时跑。

## 9. 排查清单

| 现象                                         | 检查方向                                                                                                                                                                                                                               |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 状态标签一直显示「未运行」                   | 令牌是否为空；端口是否被别的程序占了（日志 `Failed to start script API on port ...`）；点一下刷新图标                                                                                                                                  |
| 出口端口连不上                               | 是否点了「应用并重启内核」；端口是否和内核入站端口冲突（这种出口会被静默跳过，日志里有 `Skipped script outlet`）                                                                                                                       |
| 出口 IP 还是家宽 IP                          | Chrome 参数是否真的带上了 `--proxy-server`；用 `curl -x` 直接测端口排除浏览器因素                                                                                                                                                      |
| PUT 返回 404 group not found                 | 组名大小写/特殊字符是否一致；是否忘了 `encodeURIComponent`                                                                                                                                                                             |
| PUT 返回 403 managed by script outlet        | 你在切自动生成的 `PARTY-OUTLET-*` 或探测工位 `PARTY-PROBE-*` 组，改成切自己建的 select 组                                                                                                                                              |
| 切了节点但 IP 没变                           | 「切换后断开旧连接」是否关了；浏览器可能复用了长连接，可在切换后重开页面                                                                                                                                                               |
| `usable` 一直是 0                            | 看 `filter.storeSize`：`0` = 启动基线还没跑完，等一会儿或 `POST /probe`；`>0` 而 `storeAlive=0` = 确实全都不通                                                                                                                         |
| 可用节点数只有真实值的 1/5                   | 旧版本的症状，根因是 timeout=1200 那道暗门（见 7.8）。确认 `POST /probe` 响应里的 `timeout` 是 `6000`                                                                                                                                  |
| `POST /probe` 偶尔要十几秒                   | 正常。耗时 = `ceil(未命中数/150) × 6s`，按波数跳变。请求超时给到 20 秒以上，或提高 `maxAge` 提升缓存命中率                                                                                                                             |
| `mode=ip` 大量 `dial_failed`                 | 工位端口没起来（是否点了「应用并重启内核」）。工位端口不是固定区间，实际用了哪一段看启动日志 `Probe stations injected: 100 [18100-18199]`，再对着这个区间查 netstat。同一工位连续失败 5 次会被自动摘除并重新预检，日志搜 `party-probe` |
| `mode=ip` 报 `no probe station was injected` | 配置生成阶段一个工位都没注入。要么脚本 API 是关着的，要么 `18100~49151` 之间找不到连续 100 个空端口（日志 `no free window of 100 consecutive ports`）                                                                                  |
| `mode=ip` 报 `no probe station is listening` | 工位端口在册但内核还没重载出来，点「应用并重启内核」后重试                                                                                                                                                                             |
| `mode=ip` 比 delay 少一批可用节点            | 目标站点抖动造成 5~9% 假阴性，属预期。判可用性用 `mode=delay`                                                                                                                                                                          |

日志位置：Clash Party 的「日志」页面，或安装目录数据文件夹下的日志文件，搜索 `script-api` / `script outlet` 关键字。

## 11. 实例：每天自动更新「过盾」策略组

这是上面所有零件拼起来的一个完整用例：每天夜里实测一遍哪些节点能过 Cloudflare 盾，把通过的写进「过盾」策略组，然后热重载让它生效。

### 涉及的文件

| 文件                                            | 职责                                                             |
| ----------------------------------------------- | ---------------------------------------------------------------- |
| `scripts/cf-shield-probe.mjs`                   | 探测器：批量切出口 → 并发请求靶站 → 判定 → 可选写回覆写并 reload |
| `cf-shield.config.json`                         | 探测器的参数配置（靶站、超时、重试、门槛……）                     |
| `ecosystem.cf-shield.config.cjs`                | pm2 调度：每天 4 点拉起探测器，只带 `--apply`                    |
| 覆写脚本（`aggregate-groups.js`）的 AUTO 标记区 | 名单的存放位置                                                   |

### 名单为什么必须内联进覆写脚本

覆写脚本跑在 `vm` 沙箱里，上下文**只有 `console`** —— 没有 `require`、`fetch`、`fs`，而且是同步执行（`src/main/core/factory.ts` 的 `runOverrideScript`）。所以覆写脚本自己既不能探测，也不能读名单文件。名单只能作为字面量写在脚本里，由外部脚本改写文件内容。

也不能改用 YAML 覆写：`deepMerge`（`src/main/utils/merge.ts`）对数组的处理是「`+key` / `key+` 插入追加，其余整体替换」，`!` 后缀只对对象生效、**对数组无效**。在 YAML 覆写里写 `proxy-groups`，会把订阅里全部策略组一起换掉。要精确改某一个组，只有 JS 覆写这条路。

### 覆写脚本里的标记区块

```javascript
// ===== CF-SHIELD-AUTO-BEGIN 请勿手改，本区块由探测脚本整体重写 =====
const SHIELD_NODES_AUTO = []
// ===== CF-SHIELD-AUTO-END =====

const SHIELD_NODES_MANUAL = [
  // 手工兜底名单，探测挂了/结果为空时用这份
]

const SHIELD_NODES = SHIELD_NODES_AUTO.length > 0 ? SHIELD_NODES_AUTO : SHIELD_NODES_MANUAL
```

三条设计约束，都不是可选项：

- **必须留手工兜底名单。** 空的 `proxies` 是非法配置，mihomo 会直接启动失败。
- **必须做交集过滤**（`SHIELD_NODES.filter((name) => nameSet.has(name))`）。聚合订阅更新后节点名会漂移（序号重排、机场改名），名单里写了不存在的节点名同样会让内核起不来。
- **探测器只替换两个标记之间的内容**，标记行本身和 `SHIELD_NODES_MANUAL` 都不动，所以你的手工改动不会被覆盖。标记不成对时它拒绝写入。

探测器不硬编码覆写文件名：`override/` 目录用哈希 id 命名（如 `1a00025c664.js`），换机器或重建覆写就变了，所以它扫整个目录、按标记内容认领。

### 手动跑一次

```powershell

node scripts/cf-shield-probe.mjs --targets "https://nowsecure.nl/,https://discord.com/" --require all

# 探测并写入 + 热重载
node scripts/cf-shield-probe.mjs --targets "https://nowsecure.nl/,https://discord.com/" --require all --apply
```

### 参数配置文件 `cf-shield.config.json`

参数不用每次都敲在命令行上，也不该只存在 pm2 的 `args` 里 —— pm2 只负责按点把进程拉起来，参数持久化是脚本自己的事。探测器会自己找配置文件，按顺序取第一个存在的：

1. `<仓库根>/cf-shield.config.json` ← 默认就用这个
2. `<仓库根>/scripts/cf-shield.config.json`

也可以 `--settings <path>` 显式指定（相对路径按仓库根解析）。

**取值优先级：命令行 > 配置文件 > 脚本内置默认。** 配置文件是可选的，一个候选都没有就用内置默认值（启动日志会打印「参数配置 (未找到，用内置默认值)」）。

| `group`        | `--group`         |                                    |
| `maxDelay`     | `--max-delay`     |                                    |
| `limit`        | `--limit`         |                                    |
| `timeout`      | `--timeout`       |                                    |
| `require`      | `--require`       |                                    |
| `targets`      | `--targets`       | 配置文件里**可以直接写数组**       |
| `fast`         | `--fast`          | 布尔                               |
| `retry`        | `--retry`         |                                    |

仓库里那份的实际内容：

```json
{
  "targets": ["https://nowsecure.nl/", "https://discord.com/"],
  "require": "all",
  "timeout": 12000,
  "retry": 2,
  "minApply": 3,
  "dedupeIp": true,
  "outletPrefix": ""
}
```

几件要注意的事：

- **别把 `apply` 写进配置文件。** 一旦它常驻为 `true`，你随手跑一次试探测就会直接改线上覆写文件并热重载内核（连接会断一次）。让 `--apply` 只出现在 pm2 的 `args` 里，手动跑就永远是只读的。
- **别把 token 写进来。** `scriptApi.token` 由脚本自己从 Clash Party 的 `config.yaml` 读，配置文件里不需要也不应该有凭据。
- **别和 pm2 的 `ecosystem.cf-shield.config.cjs` 搞混。** 那个是调度配置（什么时候跑），这个是探测参数（怎么跑）。两者文件名都带 `.config`，而 `.json` 恰好也在 pm2 的 ecosystem 扩展名白名单里 —— 千万别对着 `cf-shield.config.json` 执行 `pm2 start`。
- 显式指定 `--settings` 却找不到文件、或 JSON 语法错、或顶层不是对象，都会**直接报错退出（exit 1）**，不会悄悄回落到默认值。文件带 UTF-8 BOM 是允许的（会自动剥掉）。
- 未指定 `--settings` 且候选路径都不存在时不报错，属正常情况。

### 用 `--outlet-prefix` 给出口分区

并发度不是脚本里的参数，而是**可用出口条数**：50 条出口就是 50 路，无条件打满。工位按下标硬绑定，第 i 个待测节点固定切到第 i 条出口（`7800`↔`出口能用01`、`7801`↔`出口能用02`……）。

想让多个脚本同时跑又不互相抢工位，就按**备注前缀**分区。`--outlet-prefix 过盾` 只会挑备注为 `过盾01` / `过盾02` / … 的出口，其余出口留给别的脚本。留空（默认）= 用全部出口。

匹配的是展开后的备注：卡片备注 `出口能用` + `count: 50` → `出口能用01`~`出口能用50`（至少补两位，`count` 超过 99 时自动补三位，与「批量新增出口」一节的规则一致）。所以 `--outlet-prefix 出口能用` 命中全部 50 条，`--outlet-prefix 出口能用0` 只命中 `01`~`09` 共 9 条。

工位清单是脚本启动时向 `GET /outlets` 取的（那个接口返回的就是展开后的逐端口列表，备注与端口都由应用算好），脚本不再自己按 `count` 推算备注。所以「批量新增出口」的备注规则改了，脚本会自动跟上。脚本只额外过滤两条：出口必须是启用状态，且必须是 direct 模式并已绑定「出口目标」—— 没绑组的出口切不了节点，当不了工位。

**前缀没匹配到任何出口时脚本直接报错退出（exit 1）**，不会静默回落成全部出口 —— 静默回落会让脚本跑到别人的分区上，比明确失败更难查。报错信息里会列出当前所有可用出口的备注，方便对照。

### 按出口 IP 去重（默认开启）

机场常把一台机器的一个 IP 拆成十几个「节点」卖（不同端口、不同协议、不同名字）。全塞进「过盾」组只会让手选列表变长，容灾能力一点没涨 —— 那台机器一挂全挂。所以探测器默认会给**已过盾**的节点再查一次出口 IP，同一个 IP 只留延迟最低的那个。

实现上的三个约定：

- **只给通过的节点查 IP。** 没过盾的不会进名单，多请求纯浪费时间。
- **去重必须在按延迟排序之后。** 代码依赖「已按延迟升序」这个前提 —— 每个 IP 首次出现的那个就是最快的，直接留它。
- **IP 查不到就保留。** 查询失败通常只是回显端点抖了一下，因为查不到把节点丢掉属于误杀。这类节点在输出里 `ip` 为 `null`，不参与去重。（`mode:"ip"` 的实现本身也警告过「ip 模式失败 ≠ 节点不可用」，实测 5~9% 假阴性，与这条约定一致。）

IP 从哪来，有两条路，优先级固定：

1. **主进程的 `POST /probe` `mode:"ip"`（首选）。** 它有一池专用探测工位（`PARTY-PROBE-*`，端口从 `18100` 起，与业务出口 `7800~7849` 完全互斥，不会互相抢），一次收 50 个节点名，内部三个回显目标并行、首成功即掐断其余两个。实测 50 个节点约 2.6 秒，全程不触发断连。走这条时 IP 是在探测全部跑完、`passList` 排序之后**一次性批量**查的。
2. **经出口端口自己请求 `--ip-url`（fallback）。** 只在应用是旧版、不认识 `mode:"ip"` 时才走：逐个节点一次请求，百量级节点会对 ipify 打上百次，有被限流的风险（限流后大量返回 null → 全被当「IP 未知」保留 → 去重形同失效，表现是 `dedupe.unknownIp` 异常大而 `dropped` 很少）。真遇到就换 `https://www.cloudflare.com/cdn-cgi/trace` 或自建端点，解析代码不用改（按正则抠第一个 IP 字面量，不假设响应格式）。

能力探测在**探测循环开始前**就做完，判据是响应里的 `mode === 'ip'` —— 旧版应用不认识 body 里的 `mode` 字段，会当成默认的延迟探测**照常返回 200**，只看状态码会误判成支持，然后每个 `ip` 都是 `undefined`，去重静默失效且日志上看不出异常。之所以不能等结果出来再决定：fallback 路径依赖「节点此刻还绑在某个出口端口上」，两条路径的时序不兼容。启动日志会打印实际走的是哪条。

输出里对应的字段：

| 位置 | 字段                     | 含义                                                         |
| ---- | ------------------------ | ------------------------------------------------------------ |
| JSON | `passed`                 | 能过盾的总数（去重前）                                       |
| JSON | `final` / `finalProxies` | 去重后真正写进「过盾」组的数量与名单                         |
| JSON | `dedupe.source`          | IP 实际来源：`station`（`mode:"ip"`）或 `ip-url`（fallback） |
| JSON | `dedupe.uniqueIps`       | 唯一出口 IP 个数                                             |
| JSON | `dedupe.unknownIp`       | IP 查询失败被保留的个数                                      |
| JSON | `dedupe.dropped[]`       | 被合并掉的节点，含 `duplicateOf`（同 IP 保留了谁）           |
| YAML | `[过盾]`                 | 去重后的名单，也是 `--apply` 写进覆写脚本的那份              |
| YAML | `[过盾-全部]`            | 去重前的全量，仅当确实有节点被合并时才生成，用于对比         |

两次实测参考：

| 时间             | 触发方式      | 候选 | 两站全过 | 去重后 | 唯一 IP | 合并掉 | IP 未知 | 生效后「过盾」成员 |
| ---------------- | ------------- | ---- | -------- | ------ | ------- | ------ | ------- | ------------------ |
| 2026-08-29 19:01 | 手动命令行    | 103  | 91       | **76** | 74      | 15     | 2       | 77（76 + 自动组）  |
| 2026-08-30 07:48 | pm2 `restart` | 108  | 101      | **73** | 71      | 28     | 2       | 74（73 + 自动组）  |

去重后的数量并不随通过数单调增长 —— 第二次通过得更多（101），但同 IP 冗余也更多（合并掉 28 个），最终名单反而少 3 个。全程约 **73 秒**（3 轮 × 50 路并发），比预估的十几分钟快得多。

### 注册成每日定时任务（pm2）

调度用 pm2，配置在仓库根目录的 `ecosystem.cf-shield.config.cjs`。

文件名的两个约束都不是可选的：pm2 靠**文件名白名单**判断传入的是配置还是要执行的脚本（`pm2/lib/Common.js` 的 `knonwConfigFileExtensions`，只认 `.json` / `.yml` / `.yaml` / `.config.js` / `.config.cjs` / `.config.mjs`），名字里缺了 `.config` 就会被当普通脚本直接跑，`apps` 里的配置全部失效；同时 `package.json` 是 `type: module`，根目录的 `.js` 会被当 ESM 解析而 pm2 用 `require()` 读配置。两条叠起来，只能叫 `*.config.cjs`。

先手动试跑一次确认能通（不写入、只测 4 个）：

```powershell
node scripts/cf-shield-probe.mjs --limit 4 --targets "https://nowsecure.nl/,https://discord.com/" --require all --timeout 12000 --retry 1
```

再注册（普通 PowerShell 即可，不需要管理员）：

```powershell
pm2 start ecosystem.cf-shield.config.cjs
pm2 stop clash-party-cf-shield
pm2 save
```

**中间那个 `pm2 stop` 不能省。** `pm2 start` 会立刻跑一次（不等 cron），而 `pm2 save` 存的是当前状态 —— 不先 stop 就会把 `online` 写进 `dump.pm2`，重启机器后 `pm2 resurrect` 会立刻拉起一次全量探测。先 stop 再 save，存进去的是 `stopped`，`resurrect` 会尊重这个状态、只等 cron 到点。这一串已实测：`resurrect` 之后 cron 仍然生效且不抢跑。

日常操作：

| 命令                                | 作用                                           |
| ----------------------------------- | ---------------------------------------------- |
| `pm2 logs clash-party-cf-shield`    | 跟踪日志                                       |
| `pm2 restart clash-party-cf-shield` | 手动立刻跑一次                                 |
| `pm2 stop clash-party-cf-shield`    | 停掉（cron 仍会到点拉起，要彻底停用就 delete） |
| `pm2 delete clash-party-cf-shield`  | 移除任务，之后记得 `pm2 save`                  |
| `pm2 install pm2-logrotate`         | 装日志轮转模块（pm2 自身不轮转）               |

日志轮转已装好（`pm2-logrotate` 3.0.0），当前设置：单个日志超 `10M` 或每天 0 点切一次，保留 `14` 份，不压缩。要改就 `pm2 set pm2-logrotate:retain 30` 这样设，`pm2 conf pm2-logrotate` 看当前值。它是全局模块，对所有 pm2 任务生效，不只这一个。

配置里两个关键字段：

- `autorestart: false` —— **硬要求**。这是一次性任务，少了这行 pm2 会在脚本正常退出后立刻重启它，变成无限循环跑探测，每轮末尾还带一次 `/reload`，等于把内核连接反复掐断。
- `cron_restart: '0 4 * * *'` —— 每天凌晨 4 点。排在夜间的原因：全量探测要跑十几分钟，且末尾那次 `/reload` 会断一次连接。

要改靶站、超时、`--min-apply` 这些，改探测器自己的 `cf-shield.config.json`（见上面「参数配置文件」一节）就行 —— pm2 的 `args` 现在只剩 `--apply`，改参数不需要动 ecosystem 配置、也不用重新 `pm2 save`。

⚠ 两个限制：探测器要经 `127.0.0.1:17890` 控制内核，所以 **Clash Party 必须在运行中**；pm2 的 cron 不唤醒睡眠的机器、也不补跑错过的时间点，4 点机器没醒就跳过这天。日志落在 `.snow/cf/logs/cf-shield-out.log` 与 `cf-shield-err.log`。

### 靶标怎么选（最容易踩的坑）

这个脚本测的是**出口 IP 声誉**，不是**客户端指纹**。

`chatgpt.com` 不能当靶标：它除了看 IP 还校验 TLS/HTTP2 指纹，Node 的 axios 走任何节点都是 403 —— 包括你本机干净的日常代理（已实测：同一代理下 chatgpt 403、claude.ai 200、discord.com 200）。拿它当靶标会把所有节点误判成不能过盾。

判断一个站能不能当靶标：**干净 IP 用 curl 直接请求能不能拿到 200**。能就可以，不能就不行。真要测 chatgpt 这类站，得上 puppeteer 跑真浏览器。

各靶站严格程度差别很大，实测参考（403 个节点、`[能用]` 组筛出 33 个候选）：

| 靶站           | 通过 |
| -------------- | ---- |
| `nowsecure.nl` | 28   |
| `discord.com`  | 29   |
| `claude.ai`    | 3    |

`claude.ai` 的 Bot 管理基本要住宅 IP，把它加进 `--require all` 会让结果极度苛刻。别用单一「过 / 不过」下结论，看结果 JSON 里 `perTarget` 对应靶站那份名单更实用。

### 重试策略

- **连接层错误（`ECONNRESET` / 超时）必须重试。** 刚切完节点内核连接还没热，同一个节点第一轮 `ECONNRESET`、第二轮 `pass` 很常见，不重试会大量误杀。
- **CF 的 challenge / 403 绝不重试。** 那是确定性结论，重试纯浪费时间。
